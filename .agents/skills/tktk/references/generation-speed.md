# 执行速度：自动补位、成批验收、直接交付

完整套图、续图、多商品和速度复盘读取一次。使用技能内现成脚本，不在普通生图任务中开发工具。提速对象是调度、重复阅读和收尾空档；商品保真、首张购买表达、自然摄影、逐页价值与每页一次修复额度不变。工具排队、生成、传输时间不能由技能保证。

## 默认快速执行路径

1. 一次看原图并记商品不变量；内部用三条短方案比较购买动机，不写长报告或增加候选图片。首张提示词就绪即提交。多产品先提交各自首张，不设置“前一套五张完成”的跨商品关口。
2. 等待期间写齐后页的准确提示词和 delivery.json。共用要求简写，每页只描述自己的镜头、动作、光线、商品与文字，不反复粘贴长篇创作分析；不得删掉商品文字、参考优先级和必要约束。人物锚点返回后，用实际衣着、发型和配件替换冲突草稿。已经派发的提示词不修改。
3. 对人物身份、商品和风格的真实依赖必须等待验收；原图负责商品，已通过的同商品图只负责人物/场景连续性。独立商品细节可以只用原图，不额外生成锚点。
4. 就绪后使用自动补位派发器：每张保存后自动 claim 空位并启动下一项，外层执行单元持续 await；不再要求模型逐张写一次“下一张”调用。默认容量2；用户要求提速且宿主允许时最多3，遇并发拒绝降低后续容量。
5. 自动窗口按“待审＋在途”限制，默认容量的两倍、最多6张；达到上限或没有就绪项即停止补位，已有请求正常收完。模型实际看完每张，用一批具体观察记录验收并领取下一批。首张/锚点可以提前单独验收释放依赖；不得让未审首图带动人物后页。
6. 最后一批实际验收和跨页核对后，同次调用完成登记与固定交付脚本。等待期间已写好的发布文案只补缺项，不在末图后写长报告、重查同一来源或临时编程。

自动补位只是调度，绝不自动判断图像质量。每张仍独立生成并逐张目视检查；工具原生图已足够判断时不重复打开。相邻页必须新增信息、动作或购买依据，不能以裁切复用充数量。未知商品事实、趋势和授权不编造。

## 队列、批量领取与连续启动

所有计划、派发记录、结果与配置写当前任务目录，不写技能目录。原图、锚点均使用绝对路径。

~~~json
{
  "capacity": 3,
  "jobs": [
    {"id":"08-01-a0","product":"08","page":1,"product_image":"<原图绝对路径>","prompt":"<完整准确提示词>","hook":"<准确叠字>","anchor_jobs":[],"depends_on":[]},
    {"id":"08-02-a0","product":"08","page":2,"product_image":"<同一原图>","prompt":"<本页完整提示词>","anchor_jobs":["08-01-a0"],"depends_on":[]}
  ]
}
~~~

~~~text
python batch_queue.py --task-dir <绝对批次目录> init --plan <计划JSON>
python batch_queue.py --task-dir <绝对批次目录> claim --limit 3 --auto-refill --pending-limit 6
~~~

使用 [batch_queue.py](../scripts/batch_queue.py)。可以先登记首张，在等待期间追加未派发后页；修改计划要原子保存，不能重置已派发任务。anchor_jobs 是传图的已验收同商品参考；depends_on 只设置真正需要的验收依赖。跨产品真实共用素材/用户指定关口才填写非空 cross_product_gate_reason，人物锚点仍不能跨商品。

claim 一次登记当前空位对应的所有就绪任务，保存实际提示词快照。单项 submit 仅供单张/明确恢复；禁止“await submit一个 → imagegen一个 → await submit下一个”，这会引入串行依赖。工具调用前后记录真实 submitted_at/returned_at，派发登记时间不冒充实际提交。

带 --auto-refill 时返回 auto_refill=true 和 pending_limit。预算同时计算已返回未验收图与在途任务，因此上限6不会被另有3张在途突破。旧式 claim 不带该标志仍可手动恢复。没有就绪项时不轮询、不固定睡眠；保留阻塞原因，待实际验收释放。

## 自动窗口派发

启动前读取 [dispatch_batch.js](../scripts/dispatch_batch.js) 原文，之后在同一 functions.exec 中读取 claim 的完整 JSON，直接 eval 可信本地脚本。批次提示词留在工具返回对象内，不反复打印给模型。claim 工具输出预算应足够容纳三条完整提示词，不能截断 JSON。

~~~javascript
// @exec: {"yield_time_ms": 120000, "max_output_tokens": 1600}
// dispatcherSource、batch 都来自本执行单元或已经完成的读取。
// claim 的 exec_command 使用 max_output_tokens: 16000。
// 不使用另一个仍运行执行单元的 store/load 传计划。
await (eval(dispatcherSource))(batch, {
  imagegen: args => tools.image_gen__imagegen(args),
  execCommand: args => tools.exec_command(args),
  emit: result => generatedImage(result),
  write: value => text(value),
  yieldControl: () => yield_control()
});
~~~

派发器同步启动一批全部 imagegen 后才 await 其他工具。每图返回后用 [image_handoff.py](../scripts/image_handoff.py) 保存、校验哈希、展示原生图，再自动领取并启动就绪项；领取和保存操作在本派发器内串行，生图请求仍可重叠。自动补位引用的参考由持久队列验证；不把刚返回未审图传给后页。

外层等待动态在途集合，不能只 await 最初三张然后退出，也不能无 await 启动后结束执行单元。每张显示后让出控制供模型查看；内部有界补位不需要模型逐张手动启动。宿主不能在让出后继续运行或不能显示逐张结果时，退回手动模式并说明限制，不声称后台自动补位已验证。

同一任务根同时只保留一个自动补位派发器。它运行时可以看图和准备具体验收意见；正常在窗口暂停/结束后成批登记，避免两个派发器抢队列锁。独立首张返回较快、需要提前释放时，可采用不带 auto-refill 的首张派发批次，模型验收后启动唯一自动派发器；不要为等待其他产品五张完工增加关口。已有自动派发器时只登记提前验收，不另开第二个自动循环；下一次领取会看见已释放的依赖。

生图错误、接收失败或队列错误停止本派发器继续补位；其他在途图片仍保存。接收失败仍展示已返回图片并保留真实路径/时间，恢复文件而非重生。若领取期间另有错误，reserved_not_started 明列尚未提交的登记项，先核对执行单元/派发文件再恢复，不能盲目重领或取消重提。

## 合并实际验收、领取和最终打包

[review_batch.py](../scripts/review_batch.py) 只登记模型已经看图得到的具体结论。将本窗口的观察作为 JSON 一次传入：

~~~json
[
  {"job_id":"08-01-a0","status":"accepted","note":"<本张商品、购买表达、摄影及文字的实际目视依据>"},
  {"job_id":"09-01-a0","status":"rejected","note":"<实际缺陷；按本页共享一次修复额度处理>"}
]
~~~

~~~text
python review_batch.py --task-dir <批次绝对目录> --reviews-json <JSON字符串> --delivery-config <预先写好的delivery.json> --set-review-note <已实际完成时才填的跨页核对意见>
~~~

用 PowerShell 单引号字面量传 JSON，并将内部单引号写成两个；不要将 JSON.stringify 当作 shell 转义。Python 参数必须先完成 shell 安全引用，禁止字符串插值引发 $() 或反引号执行。

脚本先检查所有评论、文件哈希和任务身份，再逐项落盘；空评论不能接受，拒绝项不会触发补位或导出。全部选图已通过且有实际跨页核对意见时直接调用 [deliver.py](../scripts/deliver.py) 打包一次；否则返回 batch。在同次 functions.exec 内解析返回并立即把非空 batch 传给已读取的派发器，不额外调用 next/逐项submit。

提前只登记验收、不领取时使用 image_handoff.py review；自动窗口仍存活时不要另建自动循环。脚本不会理解或验证评论真假，模型必须实际查看，绝不能预填 accepted。脚本中途失败时检查已保存状态，重跑相同验收不会重置相同结论的验收时间，也不会重生图片。

## 在等待期间完成交付配置

delivery.json 交给固定 deliver.py，不临时写导出脚本：

~~~json
{
  "agent_started_at":"<实际首个执行时间UTC；未知null>",
  "request_received_at":null,
  "products":[{
    "id":"08","name":"<ASCII英文名，最多30字符>",
    "title":"<英文标题>","caption":"<英文caption>",
    "tags":["<相关标签1>","<相关标签2>","<相关标签3>","<相关标签4>","<相关标签5>"],
    "music":"<配乐方向或核实曲目；来源与授权范围>",
    "brief":"<买家、购买理由、主行动、简短取舍和利他价值；创意假设>",
    "visual_notes":"<实际摄影方式、逐页新增信息和字体安排；商品范围>",
    "jobs":["08-01-a0","08-02-a0","08-03-a0","08-04-a0","08-05-a0"]
  }],
  "research":"<本次日期/市场/时间窗、标签和音乐来源、核实范围与限制>"
}
~~~

默认每产品5张，用户另定数量用 expected_pages。标签/音乐来源共享查询一次；不能核实时如实标注相关性建议，不称实时热门或可商用。未知挂链不编造链接CTA。

deliver.py 先核对所有选图 accepted、哈希、页序、产品、张数与产品名字数，再复制成图、写文案、打包一次并验证 ZIP内容；已有不同选图拒绝覆盖。包内正式选图与文案/记录，临时缓存不打包。压缩后 delivery_ready_at 写ZIP外 delivery-timing.json，避免为补时间重压。正常使用 review_batch.py 合并完成；单独恢复导出可直接运行 deliver.py。

## 真实计时与恢复

用同一时钟记实际提交、返回、验收和文件就绪，不每个时间点单独调用工具。消息接收和最终回复时刻只有宿主提供才记录，否则null。用户报告总耗时单列，不把 agent_started_at 至文件就绪冒充用户端总时长。

~~~text
python batch_queue.py --task-dir <批次目录> audit --started-at <实际UTC> --ended-at <实际UTC>
~~~

统计真实峰值、区间并集、最长无请求区间与收尾时间。调用重叠证明客户端同时在途，不证明GPU并行；容量、Promise数量和模拟测试不算真实提速证据。不承诺固定分钟数或百分比，不额外生测试图、不改API/模型、不加子代理、不因慢取消重提。

v0.13.0生产样本：15张、15调用、0返修，实际峰值3；agent起点至文件就绪926.576秒，打包前在途并集486.772秒、无请求437.926秒，末图至打包开始158.267秒，打包约1.878秒。主要剩余空间在提交衔接和收尾；这些时间不能全部保证消除，也不能将并集当作优化后的总耗时下限。

v0.14.0新增自动补位与合并验收/导出，本地模拟验证机制；真实提速等待下一次用户正常生成任务计时，不额外消耗生图额度。

长上下文恢复只读任务根、下一项、待审/在途ID、唯一自动派发器执行单元、修复次数和实际阻塞。准确提示词在快照文件，不回放全部历史或反复重看已通过图片。
